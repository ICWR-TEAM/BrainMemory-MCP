# 2026-08-18

## Feature — bulk tool variants for every single-item write/read tool (release v0.8.0)

### Context
Following a discussion about reducing agent token usage when using
BrainMemory-MCP (see conversation notes: brief/field projection, batching,
and a conceptual `graphify` auto-linking tool were all considered), the user
asked to implement **bulk operations first**, across every tool that
plausibly needs one.

### Problem
Every core/graph tool that mutates or fetches a *single* memory required one
MCP round-trip per item. Storing, recalling, updating, forgetting, linking,
unlinking, or annotating several memories at once meant N tool calls, each
with its own request/response overhead (tool name, JSON envelope, `status`
boilerplate) — wasted latency and tokens for batch-shaped work (e.g. bulk
import, bulk cleanup, building out a chunk of the graph).

### Fix — `src/brainmemory_mcp/server.py`
Added 7 new tools, each a thin loop over the existing singular tool's
underlying `MemoryStore` call (no `MemoryStore`/schema changes):

| New tool | Bulk equivalent of | Item shape |
|---|---|---|
| `store_memories(items)` | `store_memory` | `{content, category?, tags?, importance?}` |
| `recall_memories(memory_ids, include_connections=False)` | `recall_memory` | list of ids |
| `update_memories(updates)` | `update_memory` | `{memory_id, content?, category?, tags?, importance?}` |
| `forget_memories(memory_ids)` | `forget_memory` | list of ids |
| `add_details(items)` | `add_detail` | `{memory_id, content}` |
| `link_memories_bulk(links)` | `link_memories` | `{from_id, to_id, relation?, weight?}` |
| `unlink_memories_bulk(links)` | `unlink_memories` | `{from_id, to_id, relation?}` |

Design choices:
- **Never abort the batch.** Each item is processed independently; a missing
  id, empty content, or a self-link (`ValueError` from `MemoryStore.link`)
  produces a per-item `status: "not_found"` / `"error"` entry (with an
  `error` message) instead of raising and losing the rest of the batch.
- **Uniform response shape**: `{status: "ok", count, <verb>: <n>, results: [...]}`
  where `<verb>` is `stored`/`found`/`updated`/`removed`/`added`/`linked`/
  `unlinked` and each `results[i]` mirrors the corresponding singular tool's
  fields plus its own `status`.
- **Leaner default for `recall_memories`**: unlike `recall_memory` (which
  always includes details + connections), the bulk version defaults
  `include_connections=False` so fetching many ids stays compact; callers can
  opt into the richer per-item payload.
- **Left singular on purpose**: `search_memory`, `list_memories`,
  `recall_related`, `connect_memories`, `memory_map` — these already return
  many results from one call, or operate on a specific relationship/path, so
  a bulk wrapper would not add value.
- Server instructions text updated to point agents at the bulk tools when
  acting on multiple memories.

### Verification (smoke tests)
- `create_server()` now registers **20 tools** (was 13) + 2 resources
  (unchanged), confirmed via `FastMCP.list_tools()`.
- Exercised all 7 bulk tools directly via `FastMCP.call_tool(...)` with mixed
  batches (valid item + missing/not-found id + malformed item, and a
  self-link attempt for `link_memories_bulk`): each returned the correct
  overall count plus correct per-item `status`, and never raised /
  short-circuited on the bad item.
- `python3 -m py_compile` clean on `server.py`, `memory.py`, `__init__.py`.
